** Read-write types
:PROPERTIES:
:CUSTOM_ID: read-write-types
:END:


The [[file:documentation.org::#cons]] page will tell you that two cons variants exist: =Cons= and =&Cons=. However, this is only the tip of the iceberg. If you find the definition of the =Cons= type in =et.el=, it shows that =Cons= is merely an alias to the underlying =ConsRW= type.
#+begin_src emacs-lisp
  (et-defalias Cons [(L = Any) (R = Any)]
    (ConsRW L L R R))
#+end_src
=ConsRW= takes four arguments ~(CAR-READ CAR-WRITE CDR-READ CDR-WRITE)~.
In short, =CAR-WRITE/CDR-READ= can be thought of as the result of running =(car/cdr CONS)=, and =CAR-WRITE/CDR-WRITE= can be thought of as the type for the second parameter of ~(setcar/setcdr CONS __)~.
By necessity, =CAR-WRITE= must be a subtype of =CAR-READ= (and likewise for =CDR=), because if you can write a value with type =T= to a particular slot, then the next read will necessarily get a value of type =T=. Thus, each pair =(READ, WRITE)= can be thought of as "the range of types from =WRITE= up to =READ=", with =Never <: WRITE <: READ <: Any=.

*** Subtyping
As might be expected, =ConsRW= is covariant in its read types and contravariant in its write types. In other words, if =A= and =B= are cons types, then
#+begin_src
  A <: B iff
    CAR-READ-A  <: CAR-READ-B
    CAR-WRITE-A :> CAR-WRITE-B
    CDR-READ-A  <: CDR-READ-B
    CDR-WRITE-A :> CDR-WRITE-B
#+end_src

As shown above with =Cons=, the standard (invariant) form of a type is defined by making the =READ= and =WRITE= type identical.
The read-only (covariant) form of a type on the other hand is defined by setting making the write type =Never=. In fact, read-only aliases are generated by performing the following two transformations:
1. Modify all =RW= types so that the =WRITE= type is =Never=
2. Replace all nested aliases with its read-only equivalent

A write-only (contravariant) form of a type can be defined by setting =READ=Any=. While setting =WRITE=Never= clearly means "you cannot write to this slot", it is less clear why =READ=Any= implies write-only. A more accurate characterization would be "when you read from this slot, you have no idea what will come out."

*** Other containers
Plists, vectors, and hash tables are all defined in terms of read-write types.
#+begin_src emacs-lisp
  (et-defspec Plist (&rest args)
    (when (eq 1 (mod (length args) 2))
      (error "Plist must have an even number of arguments"))
    (cl-loop for (key type) on args by #'cddr
             nconc (list key type type) into rw-args
             finally return `(PlistRW ,@rw-args)))

  (et-defalias Vector [(E = Any)] VectorRW<E_E>)
  (et-defalias VectorW [E] VectorRW<Any_E>)

  (et-defalias HashTable [(K = Any) (V = Any)] HashTableRW<K_K_V_V>)
  (et-defalias HashTableW [(K = Any) (V = Any)] HashTableRW<Any_K_Any_V>)
#+end_src


*** So you want a write-only list
Defining contravariant types becomes very tricky with nested cons-cells. For example, suppose we wanted to define a contravariant "write-only list". We would want such a type to have the following two properties:
#+begin_src
  List<T> <: ListW<T>
  A <: B  ==>  ListW<B> <: ListW<A>   (contravariance)
#+end_src

The naive idea would be to copy the read-only version, but use the write slot instead of the read slot:
#+begin_src emacs-lisp
  (et-defalias ConsW [L R] (ConsRW Any L Any R))
  (et-defalias ListW1 [T]
    (or Nil (ConsW T ListW1<T>)))

  (et-subtype? (et ConsW<Number_Number>) (et ConsW<Integer_Integer>))
  ;; => t - the cons cell is contravariant
  (et-subtype? (et ListW1<Number>) (et ListW1<Integer>))
  ;; => nil - the list is not
#+end_src
The first cons in the list behaves as desired, however the second =cons= is stuck behind the write-only cdr of the first =cons=. In order to write to the second =cons= of a list, you must first access it, which means /reading from the cdr of the first cons/. Each step in the list is behind another contravaraint slot, giving =ListW1= a bizarre "oscillating variance" behavior:
#+begin_src emacs-lisp
  (ConsW A (ConsW B (ConsW C (ConsW D ...))))
  ;;     ^        ^        ^        ^
  ;;     |    Covariant    |    Covariant
  ;;  Contravariant   Contravariant

  (et-subtype? (et (ConsW Number (ConsW Integer (ConsW Number (ConsW Integer Nil)))))
               (et (ConsW Integer (ConsW Number (ConsW Integer (ConsW Number Nil))))))
  ;; => t
#+end_src

So just make the =cdr= invariant, right?
#+begin_src emacs-lisp
  (et-defalias ListW2 [T]
    (or Nil (ConsRW T Any ListW2<T> ListW2<T>)))

  (et-subtype? (et ListW2<Number>) (et ListW2<Integer>)) ; => nil
#+end_src
This is much better than the previous example. We can now safely traverse the list, because we know that each =cdr= that we read will be another =ListW2<T>=. Furthermore, at each step, we can /write/ a =T= to the =car= but not /read/ one, just as desired.
The issue is that =ListW2<Number>= still fails to be a subtype of =ListW2<Integer>= in the =CDR-WRITE= slot, which prevents this definition from being contravariant.

If we make the =cdr= read-only, we finally get a contravariant type:
#+begin_src emacs-lisp
  (et-defalias ListW3 [T]
    (or Nil (ConsRW Any T ListW3<T> Never)))

  (et-subtype? (et ListW3<Number>) (et ListW3<Integer>)) ; => t
  (et-subtype? (et List<Number>) (et ListW3<Number>)) ; => t
#+end_src
This has the obvious downside that a list with a read-only =cdr= cannot be appended to. The typesystem has good reason to block this kind of operation: the following example illustrates why appends are fundamentally dangerous on a contravariant list type.
#+begin_src emacs-lisp
  (et-defvar my-num-list List<Number> '(0.1 0.2 0.3))
  (et-defvar my-int-list List<Integer> '(1 2 3))

  (et-defun nconc-ints (a: ListW<Integer> b: List<Integer>) Any
    (nconc a b))

  (add-ints-to-list my-num-list my-int-list)
  ;; No problem yet, my-num-list just contains more numbers

  (nconc my-nums-to-list (list 0.4))
  ;; my-int-list now contains a float
#+end_src

In this example, the problem is not with appends themselves, but with the shared references that result from them. Motivated by this observation, we can finally define the one write-only list to rule them all:
#+begin_src emacs-lisp
  (et-defalias ListW [T]
    (or Nil (ConsRW Any T ListW<T> ListFresh<T>)))

  (et-subtype? (et ListW<Number>) (et ListW<Integer>)) ; => t
  (et-subtype? (et List<Number>) (et ListW<Number>)) ; => t
#+end_src
Hopefully you can now appreciate why contravariance is not simply "covariance in the other direction", but is rather far more intricate and complex to deal with.

** Type specs vs reprs vs objects
There are 3 different forms that a type can take.
A *type-spec* is the human-write/readable format that you will actually use in code.
A *type-expression* (=et:repr=) is a structural representation of a type-spec after being parsed.
A *type-object* (=et:type=) is a less-expressive, normalized representation of a type. Type-checking an expression evaluates to an =et:type=.

|                           | spec | et:repr | et:type |
|---------------------------+------+---------+---------|
| Human readable            | [X]  | [ ]     | [ ]     |
| Contains datatypes        | [X]  | [X]     | [X]     |
| Contains aliases          | [X]  | [X]     | [X]     |
| Contains unions           | [X]  | [X]     | [X]     |
| Contains intersections    | [X]  | [X]     | [ ]     |
| Contains type-ops         | [X]  | [X]     | [ ]     |
| Contains spec-macro calls | [X]  | [ ]     | [ ]     |
| Contains type-variables   | [X]  | [X]     | [ ]     |
| Contains variable narrows | [ ]  | [ ]     | [X]     |

#+begin_src
spec
 | Parse type syntax
 | Resolve alias/datatype/type-operation/type-variable names
 | Expand spec-macros
 V
et:repr
 | Evaluate type-operations
 | Substitute type-variables
 V
et:type
#+end_src

** Defining type operations
While defspecs operate on its arguments in unparsed form, defops allow operating on its arguments after they have already been converted to types. This makes operations much more powerful, but also more difficult to define.
#+begin_src emacs-lisp
  (et-defop NAME (ARGS...)
    [:to-string TO-STRING-CODE] ; always optional
    [:parse PARSE-CODE] ; only required for very advanced defops
    EVAL-CODE)
#+end_src
This will auto-generate functions for parsing, printing, and evaluating the operation.
The =:parse= function takes the raw spec arguments, and returns the parsed versions of the arguments (parsing the spec into the =et:repr=).
The =:to-string= function takes the parsed arguments, and returns a printed string representation.
The evaluation function takes the parsed and evaluated arguments, and returns a modified type object.

In the simplest case, where all of the arguments to the operation are types, =:parse= can be ignored. =et-defop= auto-generates a parse function which parses each spec to a =et:repr=. Additionally, the parsed arguments (in =et:repr= form) will be converted to =et:type= objects before being passed to =EVAL-CODE=. Then, =EVAL-CODE= can simply operate on the final types.
#+begin_src emacs-lisp
  (et-defop minus (a b)
    (et-subtract a b)) ; both a and b are type objects
#+end_src

Sometimes, not all arguments to an operation are types. For example, consider the =infer= operation. =infer= matches =TYPE= against =PATTERN=. If it matches, it evaluates =IF=, and if not, it evaluates =ELSE=.
Additionally, as stated before, type-arguments are automatically converted to types before being passed to =EVAL-CODE=. However, we do not want to evaluate =YES= or =NO= until we have checked whether the infer matched. So, these can be annotated with =:repr= to state that these should be passed as =et:repr= objects (not be pre-evaluated).
#+begin_src emacs-lisp
  ;; (infer TYPE [GENERICS...] PATTERN IF ELSE)
  (et (infer List<Integer> [T] List<T> T : Never)) ; => Integer
  (et (infer Boolean [T] List<T> T : Never)) ; => Never
#+end_src
The definition of =infer= looks like this:
#+begin_src emacs-lisp
  (et-defop infer (type [genvec :generics] [matcher :matcher] [yes :repr] [no :repr])
    ...)
#+end_src
Each argument (other than =type=) is paired with a keyword. The keyword specifies how the operation argument is parsed. Here, =:generics= refers to a vector of generics, =:matcher= refers to a pattern which types can be matched against, and =:repr= refers to an unevaluated type-expression.
For more information on defining advanced defops, reading through the examples defined in ~;;;; Op definitions~ in =et.el= will be far more useful than this meager docs page.

** Advanced type narrowing
Advanced narrowing will likely be useless for 99% of users, but understanding the narrowing internals can be a fun exercise if you are up for a challenge.

The =is?= and =is-a?= type utilities are very useful, but each serves a very specific purpose (although those purposes are likely sufficient for most people.) =is?= and =is-a?= are each built out of more fundamental building blocks, which could in theory be used to define more custom narrowing behaviors. These building blocks are:
- =when= - Extract the "effects" from a particular type and put it onto another type
- =supersect= - Perform an /upper-bound/ type intersection
- =minus= - Perform an /upper-bound/ type subtraction
For example, =is?= is defined as
#+begin_src emacs-lisp
  (or (when (supersect TYPE PRED) True)
      (when (minus TYPE PRED) Nil))
#+end_src
In other words, return =True= in the cases where =TYPE= overlaps with =PRED=, and =Nil= in the cases where =TYPE= differs from =PRED=.
To see how narrows propagate, watch what happens when we type-check ~(stringp obj)~:
#+begin_src emacs-lisp
  (supersect String|Number{= obj} String) => String{= obj}
  (when String{= obj} True) => True{obj : String}

  (minus String|Number{= obj} String) => Number{= obj}
  (when Number{= obj} Nil) => Nil{obj : Number}

  (is? String|Number{= obj} String) => True{obj : String} | Nil{obj : Number}
#+end_src
Similarly, =is-a?= is defined by the following:
#+begin_src emacs-lisp
  (or (when (supersect TYPE PRED) True)
      Nil)
#+end_src
The =isnt?= type utility, the opposite of =is?=, is defined by simply flipping the order of =is?=:
#+begin_src emacs-lisp
  (or (when (supersect TYPE PRED) Nil)
      (when (minus TYPE PRED) True))
#+end_src

*** Why upper-bound type-intersection?
:PROPERTIES:
:CUSTOM_ID: intersection-bounds
:END:

When intersecting or subtracting two types, a perfect answer is not always possible (e.g. intersecting =Integer= with =Positive=).
A /lower-bound intersection/, as is performed by the =subsect= utility, is guaranteed to be entirely contained within the true intersection. Namely, the =Never= type is a (trivially) valid lower-bound intersection for /any/ pair of types; For =Integer= and =Positive=, it is the /only/ valid lower-bound.
An /upper-bound intersection/, as is performed by the =supersect= utility, is guaranteed to entirely /contain/ the true intersection. For our example, both =Integer= and =Positive= would be valid upper-bound intersections, as a type itself is always guaranteed to be at least as large as its intersection with any other type.

Consider a =positivep= function, with type ~(is? T Positive)~. If =is?= used lower-bound intersection, =(positivep Integer)= would incorrectly report to never return =True=, since the lower-bound intersection of =Integer= and =Positive= would be =Never=. For this reason, upper-bound intersection (and for the same reason, subtraction) is necessary to guarantee that type-narrowing does not lie to us.
** How functions propagate recommendations
For brevity, let's define ~Pair := Cons<String_Positive>~.

An important piece of this puzzle is determining how the top-level =cons= knows what recommendations to pass to its children. The trick is to construct a function type representing the current invocation of =cons=, and compare it to the actual type of the =cons= function.
Since the invocation of =cons= is called with 2 arguments, and is recommended to return =List<Pair>=, we construct the type ~&(ARG1 ARG2) -> List<Pair>~. Compare this to the real type-signature of =cons=:
#+begin_src typescript
  invocation: &(ARG1 ARG2) -> List<Pair>
  cons: &(A B) -> ConsFresh<A_B>
#+end_src
Attempting to match ~ConsFresh<A_B>~ against ~List<Pair>~ gets us the following:
#+begin_src emacs-lisp
  ConsFresh<A_B> <: List<Pair>
  A <: Pair
  B <: List<Pair>
#+end_src
Then, we attempt to match the invocation arglist to the function arglist:
#+begin_src emacs-lisp
  &(ARG1 ARG2) = &(A=Pair B=List<Pair>)
  ARG1 = Pair
  ARG2 = List<Pair>
#+end_src
Thus, we determine argument 1 — ~(cons "Alice" 1.5)~ — should get the recommendation =Pair=, and that argument 2 — =nil= — should get the recommendation =List<Pair>=.


** Pre-processing
As with all type-checkers, multiple passes must be performed to ensure that all types are defined, and all functions/variables are given their types, before type-checking actually begins. =et= performs 3 distinct phases:
*1. Identification* - Identify all of the expressions that need to be pre-processed
*2. Pre-processing* - Pre-process all of the identified expressions
*3. Checking* - Perform type-checking

*Identification* is performed by looping through all sexps in the current buffer (and all required buffers), checking the =car= of the expression for an /identifier function/, and calling that identifier function. An identifier function returns a plist which describes how to pre-process the expression.
To add an identifier to a symbol, use =et-set-identifier=:
#+begin_src emacs-lisp
  (et-set-identifier #'defun #'et:identify-defun)
#+end_src
