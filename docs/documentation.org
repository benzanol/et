#+title: Documentation

* Overview :section:
** Introduction :section:
:PROPERTIES:
:CUSTOM_ID: introduction
:END:

=et= is an external typesystem and type-checker for elisp code, similar to [[https://www.typescriptlang.org/][Typescript]] (for Javascript) or [[https://mypy-lang.org/][mypy]]/[[https://microsoft.github.io/pyright/#/][Pyright]] (for Python).

=et= defines:

*1. A type-language for annotating elisp code*
*2. A type-checker for statically analyzing the annotated code*

*** 1. Annotating code
:PROPERTIES:
:CUSTOM_ID: annotating-intro
:END:

There are two ways to add type-annotations to your code: declare forms, and =et-annotate=.

**** Declare annotations
Type annotations can be defined using standard elisp =declare= forms, without the need for any additional dependencies.
#+begin_src emacs-lisp
  (defun add-numbers (n m)
    (declare (et (n Number) (m Number) (@return Number)))
    (+ n m))
#+end_src
- The only requirement for a function annotation is the =@return= type.
- Any parameter types which are omitted will default to the =Any= type.
- Adding ~(@skip)~ will tell the type-checker not to type-check the body of this function.

A top-level declare form can be used to define types for global variables.
#+begin_src emacs-lisp
  (declare
   (et (@variable my-number Number)
       (@variable my-local-number Number)))

  (defvar my-number 4)
  (defvar-local my-local-number 4)
#+end_src

**** et-annotate
=et-annotate.el= is a tiny package which defines several useful code-annotation macros.
#+begin_src emacs-lisp
  (et-defun add-numbers (n: Number m: Number) Number
    (+ n m))

  ;; vvv  expands to  vvv

  (cl-defun add-numbers (n m)
    (declare (et (n Number) (m Number) (@return Number)))
    (+ n m))
#+end_src
For global variables:
#+begin_src emacs-lisp
  (et-defvar my-number Number 4)
  (et-defvar-local my-local-number Number 4)

  ;; vvv  expands to  vvv

  (defvar my-number 4)
  (defvar-local my-local-number 4)
#+end_src
I will use the =et-annotate= syntax throughout this documentation; however, it is completely optional, and all of =et='s features are available without the extra dependency.

*** 2. Running the type-checker
The type-checker is built in four main layers:
1. =et.el= defines the typesystem
2. =et-check.el= defines how to type-check elisp code
3. =et-cache.el= caches results of expensive computations to improve the checker's performance
4. =et-flymake.el= uses flymake to run the type-checker in a background emacs process

To run the checker, clone the =et= repo, then add the following to your config:
#+begin_src emacs-lisp
  (add-to-list 'load-path "/path/to/et")
  (require 'et-flymake)
#+end_src
Then, navigate to the buffer you want to type-check and run
#+begin_src
  M-x et-mode
#+end_src
Keep in mind that the checker will only analyze annotated code.

You can also run =M-x et-peek= to view the inferred type of the expression in front of the point.
#+begin_src emacs-lisp
  (et-defun my-fn (x: Number) String
    (make-string (round (* x 10)) ?a))
  ; │            │      │         ╰──> Literal<97>
  ; │            │      ╰──> Number
  ; ╰─> String   ╰──> Integer
#+end_src

** Goals of the typesystem
The typesystem's design is driven by the following 3 goals:
1. *Correctness:* A successful type-check should be considered a proof of correctness, except for when the user explicitly opts out of this behavior
2. *Unobtrusiveness:* The typesystem should stay out of the user's way as much as possible. It should /not/:
  - Force the user to change how they write code
  - Fill the user's code with unnecessary type-annotations
  - Require excessive effort to get valid code to type-check
3. *Lisp-centrism:* The typesystem should be designed around Lisp's design and conventions
  - Types like lists, trees, alists, etc are all built out of a generalized =Cons= type
  - Function types are single-argument, where the argument is the entire arglist
  - Predicates and type-narrowing are first-class citizens

*** The invariance problem
A primary goal of the typesystem is /correctness/, which means that if the typesystem tells you a value will have a particular type, it will. This may seem like an obvious property for a typesystem to have, but consider the following snippet in Typescript, which is arguably the most comparable project to this one:
#+begin_src typescript
function addAnimals(animals: Animal[]) {
    animals.push(new Cat());
    animals.push(new Elephant());
}

const dogs: Dog[] = [];
addAnimals(dogs); // Dog[] is considered to be a valid Animal[]
// 'dogs' has the type Dog[], but now contains non-Dogs
#+end_src
This code will type-check in every version of Typescript. The user has done nothing wrong here, but the typesystem has failed them. The design of the typesystem is heavily motivated by the goal of addressing this problem.

** In this documentation
This documentation makes use of the following macros for demonstrative purposes:
- ~(et TYPE-SYNTAX...)~ - Parse a type
- ~(et-is? EXPRESSION TYPE)~ - Type-check =EXPRESSION=, and determine if it is assignable to =TYPE=
- ~(et-typecheck EXPRESSION)~ - Type-check =EXPRESSION= and output the resulting type

This documentation is best viewed within Emacs, where you can directly interact with the provided examples (plus create your own) to get a better feel for the system.

* Types :section:
** Type syntax
There are two mutually compatible syntaxes for defining types:
*List syntax:* ~(Cons (Vector Integer) String)~
*Symbol syntax:* ~Cons<Vector<Integer>_String>~
Symbol syntax can be nested inside of list syntax:
#+begin_src emacs-lisp
(Cons Vector<Integer> String)
#+end_src
But not the other way around:
#+begin_src emacs-lisp
Cons<(Vector Integer)_String> ; INVALID
#+end_src

** Basic types :section:
*** Scalars
The typical scalar types =String=, =Number=, and =Symbol= behave as expected for describing simple datatypes.
#+begin_src emacs-lisp
  (et-is? 4 Number) ; t
  (et-is? "foo" String) ; t
  (et-is? 'bar Symbol) ; t
#+end_src
The numeric types =Integer=, =Positive=, and =Negative= exist as subtypes of =Number=.
#+begin_src emacs-lisp
  (et-is? 4 Integer) ; t
  (et-is? 4.0 Integer) ; nil
  (et-is? 4.5 Integer) ; nil
  (et-is? 1 Positive) ; t
  (et-is? -1 Negative) ; t
  (et-is? 0 Positive) ; t
  (et-is? 0 Negative) ; t
#+end_src
The types =NonNilSymbol= (all symbols except =nil=) and =Var= (all symbols except =nil= and =t=) exist as subtypes of =Symbol=.
#+begin_src emacs-lisp
  (et-is? nil NonNilSymbol) ; nil
  (et-is? nil Var) ; nil
  (et-is? t Var) ; nil
#+end_src

There are also a host of types representing internal emacs objects, such as =Buffer=, =Window=, =Frame=, =Overlay=, etc.
#+begin_src emacs-lisp
  (et-is? (current-buffer) Buffer) ; t
  (et-is? (selected-window) Window) ; t
  (et-is? (selected-frame) Frame) ; t
#+end_src

The =Any= type matches any value, and the =NonNil= type matches any value /except/ for =nil=.
#+begin_src emacs-lisp
  (et-is? 123 NonNil) ; t
  (et-is? 'foo NonNil) ; t
  (et-is? (current-buffer) NonNil) ; t
  (et-is? nil NonNil) ; nil
  (et-is? nil Any) ; t
#+end_src

*** Literals
Any lisp value can be turned into a =Literal= type, which is a type that matches only that value.
#+begin_src emacs-lisp
  (et-is? 4 (Literal 4)) ; t
  (et-is? "foo" (Literal "foo")) ; t
#+end_src
There is also shorthand syntax for defining literal numbers, strings, and symbols:
#+begin_src emacs-lisp
  (et 4) ; (Literal 4)
  (et @foo) ; (Literal 'foo)
  (et %bar) ; (Literal "bar")
#+end_src
The types =True= and =Nil= are shorthands for =(Literal t)= and =(Literal nil)= respectively.
#+begin_src emacs-lisp
  (et True) ; (Literal t)
  (et Nil) ; (Literal nil)
#+end_src

*** Unions
Any list of types can be unioned to create a new type using the =or= utility.
#+begin_src emacs-lisp
  (et-is? 4 (or Number String)) ; t
  (et-is? "foo" (or Number String)) ; t
#+end_src
A pipe can be used as shorthand syntax for a union type.
#+begin_src emacs-lisp
  (et-is? 4 Number|String) ; t
#+end_src
The =Never= type is shorthand for an empty union, and matches no values.
#+begin_src emacs-lisp
  (equal (et (or)) (et Never)) ; t
#+end_src
Placing a question mark at the end of a type name is shorthand for unioning that type with =Nil=.
#+begin_src emacs-lisp
  (equal (et Integer?) (et Nil|Integer)) ; t
#+end_src


*** Cons (and read-write semantics)
:PROPERTIES:
:CUSTOM_ID: cons
:END:

The type ~(Cons A B)~ represents a cons cell with car =A= and cdr =B=. By default, the =Cons= type is /invariant/, meaning that cons types don't extend each other just because their argument types do. For example, a =Cons<Integer_Integer>= is not a valid =Cons<Number_Number>=. Consider the following situation:
#+begin_src emacs-lisp
  (et-defun multiply-car (cons: Cons<Number_Any>) Nil
    (setcar cons (* 1.5 (car cons))))

  (et-defvar integer-cons Cons<Integer_Integer> (cons 1 1))
  (multiply-car integer-cons)
  integer-cons ; (1.5 . 1)
#+end_src
As shown, accepting a =Cons<Integer_Integer>= as a =Cons<Number_Any>= violates correctness, and must be rejected. In order to allow for /covariance/, we must define a read-only version of a cons cell, =&Cons=. A =&Cons= cannot be written to, so =&Cons<Integer_Integer>= is a subtype of =&Cons<Number_Number>= without violating correctness.
Furthermore, a standard cons can be a subtype of a read-only cons, but not the other way around. To understand why, think about each cons type as "supporting" certain operations:
|            | car             | cdr             |
| =&Cons<A_B>= | Read =A=          | Read =B=          |
| =Cons<X_Y>=  | Read =X=, Write =X= | Read =Y=, Write =Y= |
If =X <: A= and =Y <: =B=, then =Cons<X_Y>= supports all of the operations that =&Cons<A_B>= does. Thus, =Cons<X_Y> <: &Cons<A_B>=.

For readability, types containing =Cons= and =&Cons= types are often printed in compact lisp notation:
#+begin_src emacs-lisp
  (et (Cons 1 (Cons 2 (Cons 3 Nil)))) ; (1 2 3)
  (et &Cons<1_2>) ; &(1 . 2)
  (et (Cons 1 (&Cons 2 (&Cons 3 Nil)))) ; (1 . &(2 3))
#+end_src
The underlying =Cons= types still exist, but the formatter hides them for brevity.

For advanced details on the implementation of read-only types, see [[file:implementation.org::#read-write-types]].

*** Plists
The =Plist= type represents an unordered plist, with a different type for each possible key. Similarly to =Cons=, the =Plist= type is read-write, and =&Plist= is the read-only version.
#+begin_src emacs-lisp
  (et-subtype? (et (Plist :num Integer)) (et (Plist :num Number))) ; nil
  (et-subtype? (et (&Plist :num Integer)) (et (&Plist :num Number))) ; t
#+end_src
If =nil= is a valid value for a particular key's type, then that key is optional.
#+begin_src emacs-lisp
  (et-is? '(:a 4) (&Plist :a Integer :b Integer)) ; nil
  (et-is? '(:a 4) (&Plist :a Integer :b Integer?)) ; t
  (et-is? nil (&Plist :a Integer? :b Integer?)) ; t
#+end_src

*** Functions
Functions in emacs support required, optional, rest parameters, and (with cl-lib) keyed parameters. Rather than building a function type which explicitly supports all of these features, it is much simpler to recognize that in lisp, arguments are passed to functions as a list, and that this list can be represented using the types that we already have.

For example, consider the function
#+begin_src emacs-lisp
  (et-defun foo (a: A &optional b: B c: C &rest rest: Rest) Return)
#+end_src
Note that for this function to even make sense, the type =Rest= must accept the value =nil=. A valid argument-list for this function is one of the following:
#+begin_src emacs-lisp
  (&Cons A Nil)
  (&Cons A (&Cons B Nil))
  (&Cons A (&Cons B (&Cons C Rest)))
#+end_src
We can simplify this to get the following type for the argument-list.
#+begin_src emacs-lisp
  (&Cons A (or Nil (&Cons B (or Nil (&Cons C Rest)))))
#+end_src

Now, consider a function using cl-style keyed parameters.
#+begin_src emacs-lisp
  (cl-defun bar (a: A &key x: X y: Y) Return)
#+end_src
The argument-list for this kind of function can be represented using the =Plist= type.
#+begin_src emacs-lisp
  (&Cons A (&Plist :x X :y Y))
#+end_src

Luckily, you will never need to write these out in practice. For defuns, the function type will be generated automatically. For explicitly defining function types, you can use the =args= helper to generate the arglist type.
#+begin_src emacs-lisp
  (et (fn (args Integer &optional String &rest Any) Symbol))
  ;; (Function (&Cons Integer (or Nil (&Cons String Any))) Symbol)
  (et (fn (args Integer &key :a String?) Symbol))
  ;; (Function (&Cons Integer (&Plist :a String?)) Symbol)
#+end_src
Then, function types can be expressed as follows:
#+begin_src emacs-lisp
  (et-is? #'foo (fn (args A &optional B C &rest Rest) Return)) ; t
  (et-is? #'bar (fn (args A &key :x X :y Y) Return)) ; t
#+end_src
Additionally, there are several helpers for compactly defining an =N=-argument function. If any arguments or the return value is omitted, they default to =Any=.
#+begin_src emacs-lisp
  (et fn0) ; (Function Nil Any)
  (et fn0<Integer>) ; (Function Nil Integer)
  (et fn3) ; (Function (&Cons Any (&Cons Any (&Cons Any Nil))) Any)
  (et fn3<1_2_3>) ; (Function (&Cons 1 (&Cons 2 (&Cons 3 Nil))) Any)
#+end_src

*** Other containers
The =Vector= and =HashTable= types behave very similarly to =Cons=, with read-only variants of their own.
#+begin_src emacs-lisp
  (et-subtype? (et HashTable<Integer_Integer>) (et HashTable<Number_Number>)) ; nil
  (et-subtype? (et &HashTable<Integer_Integer>) (et &HashTable<Number_Number>)) ; t
  (et-subtype? (et Vector<Integer>) (et Vector<Number>)) ; nil
  (et-subtype? (et &Vector<Integer>) (et &Vector<Number>)) ; t
#+end_src

** Type aliases
Type-aliases allow for defining new types by mapping names to type expansions. Aliases expand /lazily/, meaning that they will expand to their definition only when forced to. This feature of aliases makes defining recursive types like =List= possible.
#+begin_src emacs-lisp
  (et-defalias Boolean [] (or True Nil))
  (et-defalias List [T] (or Nil (Cons T List<T>)))
#+end_src
Defining an alias will automatically define a read-only version of that alias. This conversion is done by simply walking the definition, and replacing every read-write type with its read-only equivalent.
#+begin_src emacs-lisp
  (et-subtype? (et List<Integer>) (et List<Number>)) ; nil
  (et-subtype? (et &List<Integer>) (et &List<Number>)) ; t
  (et-expand-aliases (et &List<Integer>)) ; Nil | (&Cons Integer &List<Integer>)
#+end_src
Using a read-only version of an alias does /not/ convert the arguments to read only. For example, =&List<List<Integer>>= is a read-only list whose elements are read-write lists.
#+begin_src emacs-lisp
  (et-subtype? (et &List<List<Integer>>) (et &List<List<Number>>)) ; nil
  (et-subtype? (et &List<&List<Integer>>) (et &List<&List<Number>>)) ; t
#+end_src

Alias arguments can contain constraints on what types are valid:
#+begin_src emacs-lisp
  (et-defalias NumList [(N <: Number)]
    List<N>)
#+end_src
For multiple constraints on the same argument, use multiple forms in the vector. The parser will know that these refer to the same type-argument.
#+begin_src emacs-lisp
  (et-defalias AtleastIntList [(N <: Number) (N :> Integer)]
    List<N>)
#+end_src

** Type polymorphism
=et= also supports polymorphic function types. Polymorphic function types allow the output of a function to depend on the input of the function.
#+begin_src emacs-lisp
  (defun my-cons (a b)
    (declare (et (@generics [A B])
                 (a A) (b B)
                 (@return ConsFresh<A_B>)))
    (cons a b))
#+end_src
Equivalently,
#+begin_src emacs-lisp
  (et-defun my-cons ([A B] a: A b: B) ConsFresh<A_B>
    (cons a b))
#+end_src

Similarly to alias arguments, constraints can also be applied to function generics.
#+begin_src emacs-lisp
  (defun my-sort (nums)
    (declare (et (@generics [(N <: Number)]) (nums &List<N>)
                 (@return ListFresh<N>)))
    (sort (apply #'list nums)))
#+end_src
Equivalently,
#+begin_src emacs-lisp
  (et-defun my-sort ([(N <: Number)] nums: &List<N>) ListFresh<N>
    (sort (apply #'list nums)))
#+end_src

The function body must be type-checked without knowing what these type-variables will eventually resolve to. A type-variable is not a real type, so type-variables in the parameters are each replaced with their upper bound, and then annotated with the corresponding type variable:
#+begin_src emacs-lisp
  (et-defun my-num-cons ([A (B <: Number)] a: A b: B) ConsFresh<A_B>
    a ; => Any{$A}
    b ; => Number{$B}
    (cons a b))
#+end_src

*** Inline generics syntax
It is extremely common that a parameter's type is exactly a type variable (=left= and =right= in =cons= for example, but not =nums= in =sort=). For these cases, we introduce a shorthand syntax for defining the generic at the same time as assigning it to the parameter:
#+begin_src emacs-lisp
  (et-defun my-cons (a: [A] b: [B]) ConsFresh<A_B>
    (cons a b))
#+end_src
This syntax also allows for constraints, as follows:
#+begin_src emacs-lisp
  (et-defun my-num-cons (a: [A <: Number] b: [B <: Number]) ConsFresh<A_B>
    (cons a b))
#+end_src
The shorthand cannot express multiple constraints on a single generic; for this, the standard syntax must be used.

*** Polymorphic function types
We saw the =Function= type earlier, which is a type for a function with a fixed input and return type. The =PolyFunction= type is similar to =Function= except that its input and output are /type-expressions/ rather than single types. In addition to standard types, type-expressions can also contain type-variables, type-operations, and [[#type-variable-assignment]]s.

To define a =PolyFunction= type, add a vector of generics before the arglist type of =fn=.
#+begin_src emacs-lisp
  (et (fn [T] (args T T) ConsFresh<T_T>))
  ;; => PolyFunction<[T] &(T T) -> ConsFresh<T, T>>
#+end_src

*** Type-variable assignment :page:
:PROPERTIES:
:CUSTOM_ID: type-variable-assignment
:END:

Consider an attempt to define a generic array type consisting of both vectors and bool vectors:
#+begin_src emacs-lisp
  (et-defalias MyNaiveArray [E]
    (or Vector<E>
        BoolVector))

  (et-expand-aliases (et MyNaiveArray<Number>)) ; => Vector<Number> | BoolVector
#+end_src
However, =BoolVector= is clearly not an array of numbers. The solution is to attach a /variable assignment/ to the =BoolVector= case:
#+begin_src emacs-lisp
  (et-defalias MyArray [E]
    (or Vector<E>
        BoolVector{E:=:Boolean}))

  (et-expand-aliases (et MyArray<Number>)) ; => Vector<Number>
  (et-expand-aliases (et MyArray<Boolean>)) ; => Vector<Boolean> | BoolVector
  (et-expand-aliases (et MyArray<Any>)) ; => Vector<Any>
#+end_src
As shown, ~:=:~ only succeeds when the type variable matches exactly (it is an /invariant/ assignment). Alternatively, ~:>:~ (/covariant/ assignment) succeeds when the type variable contains its assignment, and the less common ~:<:~ (/contravariant/ assignment) succeeds when the type variable is contained within its assignment.

Since the read-only version of an alias is designed to turn the alias from invariant to covariant, it will automatically convert all /invariant/ assignments to /covariant/ ones.
#+begin_src emacs-lisp
  &MyArray<E> := &Vector<E> | BoolVector{E:>:Boolean} ; auto-generated

  (et-expand-aliases (et &MyArray<Number>)) ; => &Vector<Number>
  (et-expand-aliases (et &MyArray<Boolean>)) ; => &Vector<Boolean> | BoolVector
  (et-expand-aliases (et &MyArray<Any>)) ; => &Vector<Any> | BoolVector
#+end_src

Variable assignments can also be used to detect the appropriate type for a type variable:
#+begin_src emacs-lisp
  (et-defun my-array-get ([T] array: &MyArray<T>) T
    ...)

  (my-array-get {&Vector<Number>}) ; => Number
  (my-array-get {BoolVector}) ; => Boolean
  (my-array-get {&Vector<Number> | BoolVector}) ; => Number | Boolean
#+end_src

** Fresh types
:PROPERTIES:
:CUSTOM_ID: fresh
:END:

One unique aspect of lisp is that the same value can represent different types in different contexts. Consider the following (all valid) variable definitions:
#+begin_src emacs-lisp
  (et-defvar my-numbers List<Integer> (list 1 2))
  (et-defvar my-tuple tuple<Integer_Integer> (list 1 2))
  (et-defvar my-cons Cons<Integer_Any> (list 1 2))
#+end_src
For maximum unobtrusiveness, all of these should be accepted, as they are all perfectly valid lisp code. This begs the question, what type could =(list 1 2)= possibly return to satisfy all 3 of these cases? To answer this, we introduce /fresh types/ for representing newly created values.
#+begin_src emacs-lisp
  (et-typecheck (list 1 2)) ; ConsFresh<1, ConsFresh<2, Nil>> 
  (et-is? (list 1 2) List<Integer>) ; t
  (et-is? (list 1 2) tuple<Integer_Integer>) ; t
  (et-is? (list 1 2) Cons<Integer_Any>) ; t
#+end_src
Unlike other container types, which care about read-write permissions, fresh types only care about structure: a fresh type can be assigned to any type which it is /structurally compatible/ with.

*** Automatic unfreshening
Fresh types are extremely powerful, but also extremely dangerous. Imagine that we allowed fresh types to propagate through function calls:
#+begin_src emacs-lisp
  (et-defun cons-same (value: [T]) ConsFresh<T_T>
    (cons value value))

  (et-defvar my-var (Cons Cons<Integer_Integer> Cons<Number_Number>)
    (cons-same (cons 1 2))) ; => (ConsFresh ConsFresh<1_2> ConsFresh<1_2>)

  (setcar (cdr my-var) 1.5)
  (car (car my-var)) ; Type-checks as Integer, but is actually 1.5
#+end_src
The newly-created cons cell is simultaneously assigned to a ~Cons<Integer_Integer>~ and to a ~Cons<Number_Number>~, which results in a correctness bug.
 To remedy this, fresh types can exist only temporarily. A fresh type must resolve to a concrete type as soon as a value is used (passed to another function, assigned to a variable, etc). In the example above, we instead have
#+begin_src emacs-lisp
  (cons-same (cons 1 2)) ; => (ConsFresh &Cons<1_2> &Cons<1_2>)
#+end_src
because ~ConsFresh<1_2>~ is automatically unfreshened to ~&Cons<1_2>~ before passing it to =cons-same=.

*** freshen-deep and freshen-shallow
The =freshen-deep= and =freshen-shallow= type utilities can be used to turn a concrete type into an equivalent fresh type:
#+begin_src emacs-lisp
  (et-defun list (&rest objects: [T]) (freshen-shallow T))
  (et-defun copy-tree (x: [T]) (freshen-deep T))

  (et-defvar my-nested-list List<List<Integer>> nil)
  (apply #'list my-nested-list) ; => ListFresh<List<Integer>>
  (copy-tree my-nested-list) ; => ListFresh<ListFresh<Integer>>
#+end_src

** Structs
When using =cl-defstruct=, the =:et= slot property can be used to indicate the type of a struct's slots. Slots without an =:et= property are given the =Any= type.
#+begin_src emacs-lisp
  (cl-defstruct my-person
    (name "" :et String)
    (age 0 :et Integer))
#+end_src

The type ~(Struct my-person)~ refers to instances of the =my-person= struct. The shorthand ~*my-person~ is equivalent, however the longer form may still need to be used for structs whose names contain characters which break et's parsing.

From a struct definition, the type-checker will generate definitions for the struct's constructor, predicate, copier, and accessors.
#+begin_src emacs-lisp
  (make-my-person :name "John" :age 35) ; => *my-person
  (my-person-name {*my-person}) ; => String
  (copy-my-person {*my-person}) ; => *my-person
  (my-person-p {x : *my-person|Other}) ; => t{x : *my-person} | nil{x : Other}
#+end_src
For more information on the predicate return type, see [[#narrowing]].

*** Generic structs
To make a struct type generic, add an =:et-generics= property to the first slot.
#+begin_src emacs-lisp
  (cl-defstruct my-pair
    (first nil :et-generics [T] :et T)
    (second nil :et T))
#+end_src
The type ~(Struct my-pair Integer)~, or equivalently ~*my-pair<Integer>~, represents a =my-pair= struct with ~T=Integer~.
Generic constraints use the same syntax as aliases and polymorphic functions:
#+begin_src emacs-lisp
  (cl-defstruct my-numeric-pair
    (first 0 :et-generics [(T <: Number)] :et T)
    (second 0 :et T))
#+end_src
Struct type arguments are invariant, since struct slots can be mutated. Thus, =*box<Integer>= is not a subtype of =*box<Number>=.

** Narrowing
:PROPERTIES:
:CUSTOM_ID: narrowing
:END:

A common pattern in lisp is using predicates to handle a value differently based on its runtime type.
#+begin_src emacs-lisp
  (et-defun my-repeat (repeat: Integer obj: Integer|String) String
    (if (stringp obj)
        (s-repeat repeat obj)
      (make-string repeat obj)))
#+end_src
Within the =then= branch of the if-statement, we want the type of =obj= to be narrowed to just =String=, and likewise to just =Integer= in the else branch.
To solve this, we introduce narrow-binding. Narrow-binds allow a type to contain internal information about variables in scope.
#+begin_src emacs-lisp
  (stringp obj) ; :: True{obj : String} | Nil{obj : Integer}
#+end_src

This type describes that when it is true, =obj= has type =String=, and when it is nil, =obj= has type =Integer=. Utilizing this, conditional macros such as =if= can type-check each branch with the correct narrowed variable types.
In order for this to work, the type returned by a variable must not only contain the type of the value, but also encode that the type represents the value currently stored in =obj=.
#+begin_src emacs-lisp
  obj ; :: Integer|String {= obj}
#+end_src
This type describes that it is an =Integer= or =String=, and also that whatever value it holds is equal to the value stored in the variable =obj=. This allows for narrowing not just on predicate outputs, but on variables themselves:
#+begin_src emacs-lisp
  (et-defun my-negative (val: Number?) Number
    (if val
        (- val) ; val : Number
      0)) ; val : Nil
#+end_src

*** Defining predicate functions
To define a function which narrows an argument, the value being narrowed must be assigned to a generic type parameter. Then, the =is?= type operation can be used in the return:
#+begin_src emacs-lisp
  (et-defun my-stringp (s: [S]) (is? S String)
    (stringp s))
#+end_src
Then, suppose you type-check the expression
#+begin_src emacs-lisp
  (stringp obj)
#+end_src
As discussed, =obj= will evaluate to the type ~String|Integer {= obj}~. When type-checking the call to =my-stringp=, this type will get assigned to =S=. The =is?= type-utility then does the following conversion:
#+begin_src emacs-lisp
  (is? String|Integer{=obj} String)
  => True{obj : String} | Nil{obj : Integer}
#+end_src

Now, consider the behavior of a =not=-like function:
#+begin_src emacs-lisp
  (et-defun my-not (bool: [T]) (is? T Nil)
    (not bool))
#+end_src
If we evaluate ~(my-not (my-stringp obj))~, then we will get the conversion
#+begin_src emacs-lisp
  (is? {True{obj : String} | Nil{obj : Integer}} Nil)
  => True{obj : Integer} | Nil{obj: String}
#+end_src
This is exactly the behavior we would want out of this expression, and we get it nearly for free.

*** Additional narrowing operations
Not all predicates exhaustively classify an entire type. For example, =evenp= returns =t= only for integers, but not for /all/ integers. For predicates like this, use the =is-a?= operation.
#+begin_src emacs-lisp
  (et-defun my-evenp (val: [T]) (is-a? T Integer)
    (and (integerp val) (evenp val)))
#+end_src
Then, if we evaluate ~(my-evenp obj)~, we get the following conversion
#+begin_src emacs-lisp
  (is-a? String|Integer{= obj} Integer)
  => True{obj : Integer} | Nil{obj: String|Integer}
#+end_src
If ~(my-evenp obj)~ returns =t=, the typesystem can conclude that its input was definitely an integer, but if it returns =nil=, it cannot make a similar conclusion in the reverse direction.

The =isnt?= operation is the opposite of =is?=.
#+begin_src emacs-lisp
  (et-defun my-atom (val: [T]) (isnt? T &Cons<Any_Any>)
    (atom val))
#+end_src

** Type operations
:PROPERTIES:
:CUSTOM_ID: type-operations
:END:

Type-operations define arbitrary transformations between types.
#+begin_src emacs-lisp
  (et (minus Boolean Nil)) ; => True
#+end_src
This is fairly useless when using concrete types: you could have just written ~(et True)~. Type-operations become much more useful when applied to type-variables:
#+begin_src emacs-lisp
  (et-defun my-remove-nil ([T] list: &List<T>) (List (minus T Nil))
    (remq list nil))

  (my-remove-nil {List<Boolean>}) ; => List<True>
#+end_src

We have already seen the type-operations =is?=, =is-a?=, and =isnt?=, which are used for type-narrowing. A list of type operations can be found [[#type-operations-ref][here]].

** Spec macros
A "spec" is the human-writable list format which eventually gets parsed into actual type object. =et-defspec= can be used to define a custom spec-macro, which expands one spec to another spec before it is parsed into a type object.
#+begin_src emacs-lisp
  (et-deftype tuple (&rest args)
    (if (null args) '(Nil)
      `(Cons ,(car args) (tuple ,@(cdr args)))))

  (et tuple 1 2 3) ; => (Cons 1 (Cons 2 (Cons 3 Nil)))
#+end_src
Keep in mind that the spec returned by a spec-macro cannot use the *symbol syntax* for types, it must use *list syntax*. This includes wrapping even zero-argument types in a list (as shown above with =Nil=).
Many types you have seen so far, such as =args=, and =fn=, are actually spec macros which expand to real types. It is generally convention that spec-macros and type-operations are /lowercase/, while core datatypes and aliases are uppercase.

* Type-checking :section:
** Type-checking (bottom-up)
Expression checking is primarily done bottom-up. That is, the most deeply nested expressions are evaluated first, and their types are propagated upward in order to determine correctness.
#+begin_src emacs-lisp
  (string-width (concat "a" "b"))
#+end_src
In this example, the first expressions evaluated are ="a"= and ="b"= , which each return literal types corresponding to their exact values.
The next expression evaluated is ~(concat "a" "b")~. The arglist type ~&("a" "b")~ is matched against the function type ~&List<String> -> String~, determining that the expression returns =String=.
Finally, the top-level expression is evaluated. The arglist type =&(String)= is matched against the function type ~&(String) -> Integer~, determining that the expression returns =Integer=.

** Recommendations (top-down)
The correctness and types of the program are all determined bottom-up as described previously, but inner expressions sometimes need to be /nudged in the right direction/. Consider the following example:
#+begin_src emacs-lisp
  (et-defvar my-list List<Cons<String_Positive>>
    (cons (cons "Alice" 1.5) nil))
#+end_src
~(cons "Alice" 1.5)~ evaluates to the type ~ConsFresh<"Alice"_1.5>~; however, as described in [[#fresh]], this must be resolved to a concrete cons type before proceeding. Of the many options it has to resolve to, we can clearly see that it /should/ choose ~Cons<String_Positive>~, but it needs some way to know that. To make this possible, a /type-recommendation/ must be passed down when traversing an expression.
=et-defvar= type-checks the top-level =cons= with the recommendation ~List<Cons<String_Positive>>~. Based on this, =cons= calculates that it should give its first child the recommendation ~Cons<String_Positive>~. Then, when ~(cons "Alice" 1.5)~ is converted to a concrete type, it uses the recommendation as a hint, and returns the correct type.

** Casting
Sometimes, type-recommendations will not be enough to coerce an expression to the desired type. In this case, there are several macros that allow explicitly overriding the recommendation system.
The =et:= macro, or /safe cast/, can be used to safely cast an expression to a particular type. Its safety comes from the fact that the type of the expression must be compatible with the type it gets cast to, guaranteeing that correctness will not be compromised.
#+begin_src emacs-lisp
  nil ; => Nil
  (et: List<Integer> nil) ; => List<Integer>
  (et: Vector<Integer> nil) ; => error - expected Vector<Integer>, found Nil
#+end_src

The =et!= macro, or /unsafe cast/, can be used to cast an expression to any arbitrary type, regardless of the type actually returned by the expression. For obvious reasons, the use of this macro compromises correctness.
#+begin_src emacs-lisp
  (et! Vector<Integer> nil) ; => Vector<Integer>
#+end_src

** Variable inference
When defining a variable in a let-binding, it is often unclear just from the initial value what the type should be. There are an infinite number of types that might be intended when initializing a variable as =nil= in a let binding.
#+begin_src emacs-lisp
  (let ((stack nil)
        (finished nil)
        (i 0))
    (while (not finished)
      (setq stack (cons i stack))
      (setq i (1+ i))
      (when (eq i count) (setq finished t)))
    stack)
#+end_src

One solution to this is to explicitly widen the type of each value:
#+begin_src emacs-lisp
  (let ((stack (et: List<Integer> nil))
        (finished (et: Boolean nil))
        (i (et: Integer 0)))
    ...)
#+end_src
This works, but requires significantly changing the way that the developer writes code.

Instead, when checking a =let= expression, =et= will perform a first pass over the body and determine each place that a variable is used. Then, it will make a /best guess/ for what the variable type should be, and proceed with type-checking using the best-guess type. This will eliminate the need for explicitly casting the value to the correct type.
In this example, the first pass yields the following requirements:
#+begin_src emacs-lisp
  typeof stack :> nil, ConsFresh<typeof i, typeof stack>
  typeof i :> 0, Integer
  typeof finished :> True, Nil
#+end_src
Solving these equations yields a type of =Integer= for =i=, =List<Integer>= for =stack=, and =True|Nil= for =finished=.


** Implicit function overloads
Many languages allow for function overloading, where the same function has multiple signatures. Elisp lacks explicit overloading, but many functions still exhibit overload-like behavior: their return types vary based on flags, argument types, etc.
For example, a (somewhat) common pattern in elisp is for a function to provide a =noerror= flag. If this flag is non-nil, then the function will return the value =nil= instead of throwing an error if it fails. This can be expressed by the typesystem as follows:
#+begin_src emacs-lisp
  (et-defun my-string-search (pattern: String &optional noerror: [N])
            (is-nil? N String String?)
    (let* ((result (search-for pattern))) ; => result : String?
      (if noerror
          result ; => String?
        (or result (error "No result found!"))))) ; => String

  (my-string-search "foo") ; => String
  (my-string-search "foo" nil) ; => String
  (my-string-search "foo" t) ; => String?
  (my-string-search "foo" {Any}) ; => String?
#+end_src
This says that if =noerror= is /definitely/ nil, then the function definitely returns a non-nil =String=. If there is even a slight chance that =noerror= is non-nil, then it returns =String?=.

How can the typesystem possibly verify that the body of the function conforms to this complex set of rules? The answer is /implicit overloads/.
Upon seeing ~(is-nil? N String String?)~, the typesystem implicitly generates two overloads for =my-string-search=:
#+begin_src emacs-lisp
  1. (pattern: String &optional noerror: [N <: Nil]) -> String
  2. (pattern: String &optional noerror: [N !<: Nil]) -> String?
#+end_src
In the first overload, =N= is constrained to be a subtype of =Nil=. With this constraint, the return type of the function collapses to just =String=. In the second overload, =N= is constrained to NOT be a subtype of =Nil=, in which case the return type collapses to =String?=.
The function is then type-checked twice, once for each overload. For overload 1, the type-checker determines that =noerror: Nil=, so only the /else/ branch can ever be reached. Thus, the body correctly returns =String=. On the other hand, the condition =[N !<: Nil]= cannot make any guarantees about =noerror=. For example =Any !<: Nil=, in which case =noerror= could be any value. Thus, overload 2 evaluates both branches of the if statement, and finds that the body correctly returns =String?=.

Another common example of overloaded functions are /arithmetic operations/. These can be represented without overloads as follows:
#+begin_src emacs-lisp
  (et-defun + (&rest nums: [Ns <: &List<Number>])
            (switch Ns [Nil 0] [&List<Integer> Integer] Number)
    ...)

  (+) ; => 0
  (+ 1 2) ; => Integer
  (+ 1 2.5) ; => Number
#+end_src
The =switch= type operation checks =Ns= against each case. If =Ns <: Nil=, it returns =0=. If =Ns <: &List<Integer>=, it returns =Integer=. Otherwise, it returns =Number=.

** Macro checkers
Type-checking macros is substantially different than type-checking functions. While a function type models a /type transformation/, a macro checker must instead model /control-flow/.
For this, we introduce "checker expressions". A checker expression is built out of building blocks, each representing a common control-flow pattern.

*** $expand
Many simple macros can get away with just using the =$expand= checker. This tells the type-checker to expand the macro, and then type-check the resulting expression, instead of trying to type-check the original macro invocation.
#+begin_src emacs-lisp
  (defmacro my-increment (place)
    (et ($expand))
    `(setf ,place (1+ ,place)))
#+end_src

*** $body
Many macros take a fixed number of positional arguments (zero or more), and the remaining arguments are expressions to be evaluated. The =$body= checker can be used in this case:
#+begin_src emacs-lisp
  (defmacro save-excursion (&rest body)
    (et ($body))
    ...)
  (defmacro with-current-buffer (buf &rest body)
    (et ($body Buffer))
    ...)
#+end_src

*** Some utility checkers
The following can be used as building blocks for defining more complex checkers:
- =($at PATH...)= traverse the current expression using =PATH=, and type-check that sub-expression.
- =($tail PATH...)= traverse the current expression using =PATH=, and type-check that sub-expression and all remaining sub-expressions of its parent. Return the last type.
- ~($tail-tuple PATH...)~ like =$tail=, but return a tuple type containing the types of all of the tail entries.
- ~($exp EXPR)~ type-check the expression =EXPR=.
- ~($exps EXPRS)~ type-check the expressions =EXPRS=, returning the type of the last one.
- ~($type TYPE-SPEC)~ do nothing and return the type =TYPE-SPEC=.
- ~($nil)~ do nothing and return the type =Nil=.
- ~($progn CHECKERS...)~ perform the checks specified by =CHECKERS=, and return the last one.
- ~($prog1 CHECKERS...)~ perform the checks specified by =CHECKERS=, and return the first one.
- ~($ignore CHECKERS...)~ perform the checks specified by =CHECKERS=, and return =Nil=.
- ~($with-rec REC-CHECKER CHECKER)~ perform the check specified by =REC-CHECKER=, and set the current type-recommendation to its return type. Then, perform the checks specified by =CHECKER=.
- ~($expect EXPECTED-CHECKER CHECKER)~ similar to =$with-rec=, but throw an error if the type returned by =CHECKER= is not a subtype of the expected type.

These checkers all implement fairly linear control-flow. There are numerous other checkers for checking non-linear control flow, such as =$branches=, =$loop=, =$if=, and many others. This documentation needs to be expanded to contain in-depth explanations of each of these checkers.

*** Pattern matching
The =$pcase= checker can be used to match the macro's arguments, and route to different checkers based on the matched branch. The following is the real checker for =let*=:
#+begin_src emacs-lisp
  ($pcase
   `(() . ,_body) ($tail 2)
   `((,first . ,rest) . ,body)
   ($exp `(let (,first) (let* ,rest ,@body))))
#+end_src
Here, ~($tail 2)~ type-checks the expression's tail, starting at index 2. For =let*=, this is the body. ~($exp (let (,first) ...))~ type-checks a =let= expression containing just the first binding, whose body recursively references =let*=. This will recurse until each binding of the original =let*= has been processed individually within its own =let=.

Alternatively, the =$arglist= checker destructures the arguments like a function arglist.
#+begin_src emacs-lisp
  (defmacro my-increment (place)
    (declare
     (et ($arglist (p) ($exp `(setf ,p (1+ ,p))))))
    ...)
#+end_src
This checker tells the type-checker that when it encounters ~(my-increment PLACE)~, it should instead type-check the expression ~(setf PLACE (1+ PLACE))~. It is often easier to describe how to check a macro in terms of an equivalent expression rather than trying to describe its functionality from the ground up.

* Reference :section:
** Declare forms
This page refers to /top-level declare forms/, which are defined at the top level of the file. For function-level declare forms, see [[#annotating-intro]].

Top-level declare forms can be defined in one of two ways.
Without any dependencies:
#+begin_src emacs-lisp
  (declare
   (et (@declare-form-1 ...)
       (@declare-form-2 ...)))
#+end_src
With =et-annotate= as a dependency:
#+begin_src emacs-lisp
  (et-declare
   (@declare-form-1 ...)
   (@declare-form-2 ...))
#+end_src

*** @def
Declare a function's type.
#+begin_src emacs-lisp
  (et-declare
   (@def my-fn (param1: Type1 param2: Type2) ReturnType)
   ;; With generics
   (@def my-generic-fn ([T (N <: Number)] obj: T nums: List<N>) Alist<N_T>)
   ;; With inline generics
   (@def my-inline-generic-fn (obj: [T] nums: [N <: Number]) Alist<N_T>))
#+end_src

*** @check
Declare a checker for a macro.
#+begin_src emacs-lisp
  (et-declare
    ;; A macro which can be type-checked by simply expanding it
    (@check my-simple-macro ($expand))
    ;; A macro which takes a string argument, and the rest is the body
    (@check my-with-default-directory ($body String))
    ;; Type check this macro by checking some other equivalent expression
    (@check my-increment ($arglist (p) ($exp `(setf ,p (1+ ,p))))))
#+end_src

*** @variable
Declare a variable's type.
#+begin_src emacs-lisp
  (et-declare
   (@variable my-variable Type))
#+end_src

*** @alias
Define an alias.
#+begin_src emacs-lisp
  (et-declare
   (@alias MyIntList List<Integer>)
   ;; With a type parameter
   (@alias MySymbolAlist [V] Alist<Symbol_V>)
   ;; With a default value for a type parameter
   (@alias MyOtherAlist [K (V = Any)] Alist<K_V>)
   ;; With a constraint and a default value on the same type parameter
   (@alias MyNumberAlist [K (V <: Number) (V = Integer)] Alist<K_V>))
#+end_src

*** @spec
Define a custom spec macro.
#+begin_src emacs-lisp
  (et-declare
   (@spec my-cons (&optional arg1 arg2)
          `(Cons ,(or arg1 'Any) ,(or arg2 arg1 'Any))))
#+end_src

*** @symbol-property
To get accurate types for =put= and =get=, you can declare a particular symbol-property to have a particular type.
#+begin_src emacs-lisp
  (et-declare
   (@symbol-property my-documentation String))

  (get SYMBOL 'foo) ; => Any
  (get SYMBOL 'my-documentation) ; => String?
#+end_src

*** @eval
Run some elisp code within the checker process.
#+begin_src emacs-lisp
  (et-declare
   (@eval (setq et-allow-unrecognized nil)))

  ;; et will complain about this unrecognized top-level form
  (my-unrecognized-function)
#+end_src

** Type operations
:PROPERTIES:
:CUSTOM_ID: type-operations-ref
:END:


*** extends?
~(extends? CHILD PARENT IF ELSE)~

Check whether =CHILD= is a subtype of =PARENT=.
#+begin_src emacs-lisp
  (et (extends? Integer Number 1 0)) ; => 1
  (et (extends? String Number 1 0)) ; => 0
  ;; The type variable COULD represent a subtype of Number, or it might not
  (et-with-type-variables [T] (et (extends? T Number 1 0))) ; => 1 | 0
#+end_src

*** infer
~(infer TYPE [GENERICS] PATTERN IF ELSE)~

Match =type= against =pattern= and determine values for each of the =generics=. If it matches, then evaluate =if= with the inferred generics. Otherwise, return =else=.
#+begin_src emacs-lisp
  (et (infer List<Integer> [T] List<T> T Never)) ; => Integer
  (et (infer String [T] List<T> T Never)) ; => Never
#+end_src

*** minus
~(minus A B)~

Subtract =B= from =A=.
#+begin_src emacs-lisp
  (et (minus Number|String Number)) ;; => String
  (et (minus List<Integer> Nil)) ;; => (Integer . List<Integer>)
#+end_src
There is not always a perfect answer for type-subtraction. In such cases, =minus= will always err on the side of keeping the type /larger/ than it should be. See [[#intersection-bounds]].
#+begin_src emacs-lisp
(et (minus Number Integer)) ;; => Number
#+end_src

*** subsect/supersect
~(subsect A B)~ / ~(supersect A B)~

Perform lower/upper bound intersection.
#+begin_src emacs-lisp
  (et (subsect Integer Positive)) ; => Never
  (et (supersect Integer Positive)) ; => Integer

  (et (supersect (fn1 Integer Integer) (fn1 Number Number)))
  ;; => Function<&(Number), Integer>

  (et (supersect AnyFn Cons<Any_Any>)) ; => Function<Never, Any>
  (et (supersect AnyFn Cons<Integer_Any>)) ; => Never
  (et (supersect AnyFn Cons<@foo_Any>)) ; => Never
  (et (supersect AnyFn Cons<@lambda_Any>)) ; => Function<Never, Any>
#+end_src

*** freshen-deep/freshen-shallow
~(freshen-deep TYPE)~ / ~(freshen-shallow TYPE)~

Convert a type to its freshened version.
=freshen= will recursively freshen every level of the type, like ~(copy-tree value)~.
=freshen-shallow= will only freshen the top-level list, like ~(apply #'list value)~
#+begin_src emacs-lisp
  (et (freshen-deep List<List<Integer>>))
  ;; => ListFresh<ListFresh<Integer>>
  (et (freshen-shallow List<List<Integer>>))
  ;; => ListFresh<List<Integer>>
  (et (freshen-deep (Cons (Cons 1 2) (Cons 3 4))))
  ;; => (ConsFresh (ConsFresh 1 2) (ConsFresh 3 4))
  (et (freshen-shallow (Cons (Cons 1 2) (Cons 3 4))))
  ;; => (ConsFresh (Cons 1 2) (ConsFresh 3 4))
#+end_src

** Provided spec macros
*** tuple/tuple*
~(tuple TYPES...)~ / ~(tuple* TYPES... TAIL)~

#+begin_src emacs-lisp
  (et (tuple 1 2 3)) ; => (Cons 1 (Cons 2 (Cons 3 Nil)))
  (et (&tuple 1 2 3)) ; => (&Cons 1 (&Cons 2 (&Cons 3 Nil)))

  (et (tuple* 1 2 3)) ; => (Cons 1 (Cons 2 3))
  (et (&tuple* 1 2 3)) ; => (&Cons 1 (&Cons 2 3))
#+end_src

*** args
~(args SPECS...)~

#+begin_src emacs-lisp
  (et (args A B C)) ; => &(A B C)

  (et (args Integer &optional String &rest Any))
  ;; => &(Integer . Nil | &(String . Any))

  (et (args String &key :flag Boolean :count Integer))
  ;; => &(String . &Plist<:flag Boolean, :count Integer>)
#+end_src

*** fn
~(fn [GENERICS?] ARGS RETURN)~

#+begin_src emacs-lisp
  (et (fn (args Integer String) Boolean))
  ;; => (Function &(Integer String) Boolean)
  (et (fn [T] (args T T T) List<T>))
  ;; => (PolyFunction &(T T T) List<T>)
#+end_src

*** fnN
~(fnN ARGS... RETURN?)~

The explicit =return= type can be omitted, in which case the return type will default to =Any=.
#+begin_src emacs-lisp
  (et (fn0 Integer)) ; => (Function Nil Integer)
  (et (fn1 4 Integer)) ; => (Function &(4 . Nil) Integer)
  (et (fn2 4 3 Integer)) ; => (Function &(4 3) Integer)
  (et (fn1 4)) ; => (Function &(4) Any)
#+end_src

*** switch
~(switch TYPE CASES...)~

Each case is either
- ~[TYPE OUTPUT]~ 
- ~[[GENERICS] PATTERN OUTPUT]~
If the pattern and output happen to be the same, then you can use the shortcut:
- ~[[GENERICS] PATTERN-AND-OUTPUT]~

#+begin_src emacs-lisp
  (et-defalias SumOf [(Nums <: &List<Number>)]
    (switch Nums
            [Nil 0]
            [[T] &tuple<T> One]
            [&List<Integer> Integer]
            Number))
  ;; Expands to:
  (extends? Nums Nil 0
            (infer? Nums [T] &tuple<T> T
                    (extends? Nums &List<Integer> Integer
                              Number)))

  (et-expand-aliases (et SumOf Nil)) ; => 0
  (et-expand-aliases (et SumOf (Cons 123 Nil))) ; => 123
  (et-expand-aliases (et SumOf (tuple 2 3))) ; => Integer
  (et-expand-aliases (et SumOf (tuple 1.5 2))) ; => Number
#+end_src

The final case can be a single default type, which will be returned if no cases match. If a default type is not provided, =Never= will be used as the default.


*** map-cases
~(map-cases TYPE CASES...)~

One limitation of =switch= is that it is limited when the input is a union. =map-cases= is like =switch=, except cases can match /partially./ If a case matches only partially, the rest of the type will continue through the remaining cases, until the entire type has been matched.

If the cases collectively match the entire type, then the result will be the union of the outputs of the matching cases. If part of the type is /not/ matched by any type, the result will be =Never=.

#+begin_src emacs-lisp
  (et-defalias ExampleElementOf [Seq]
    (map-cases Seq
               [[T] &List<T> T]
               [[T] Vector<T> T]
               [BoolVector Boolean]))

  (et-expand-aliases (et ExampleElementOf List<Integer>|Vector<Integer>))
#+end_src

*** might-overlap?
~(might-overlap? A B YES NO)~
Evaluates to ~(extends? (supersect A B) Never NO YES)~

If =A= and =B= have any chance of intersection, return =YES=, otherwise return =NO=.
If =NO= is omitted, it defaults to =Never=.
#+begin_src emacs-lisp
  (et (might-overlap? Integer|String Boolean|String True Nil)) ; => True
  (et (might-overlap? Integer|String Boolean True Nil)) ; => Nil
  (et (might-overlap? Integer|String Boolean True)) ; => Never
  (et (might-overlap? Integer Positive True)) ; => True
#+end_src

*** non-nil

** Provided aliases
This is a collection of some of the more useful aliases built into the typesystem.
#+begin_src emacs-lisp
  (et-defalias Boolean [] (or Nil True))
  ;; Most places that take a boolean can actually take anything.
  ;; Use Bool for these instead of Any to make it more clear
  (et-defalias Bool [] Any)

  ;; All functions are a subtype of AnyFn
  (et-defalias AnyFn [] (Function Never Any))
  (et-defalias IdFn [T] (Function T T))
  (et-defalias Sink [T] (Function (args T) Nil))

  (et-defalias IntOrMarker [] (or Integer Marker))
  (et-defalias NumOrMarker [] (or Number Marker))

  (et-defalias List [(E = Any)] (or Nil (Cons E (List E))))
  (et-defalias ListFresh [(E = Any)] (or Nil (ConsFresh E (ListFresh E))))

  (et-defalias ListWithLast [E Last]
    (or (Cons Last Nil)
        (Cons E ListWithLast<E_Last>)))
  (et-defalias AppendLast [T]
    (map-cases T
               [[X] &Cons<X_Nil> X]
               [[A B] &Cons<A_B> &Cons<A_AppendLast<B>>]))

  (et-defalias Tree [(E = Any)] (or (List (Tree E)) E))
  (et-defalias ConsTree [(E = Any)] (or (Cons (ConsTree E) (ConsTree E)) E))

  (et-defalias Alist [K V] (List (Cons K V)))

  (et-defalias PlistOf [K V] (or Nil (Cons K (Cons V (PlistOf K V)))))

  (et-defalias PlistLike [K V]
    (or PlistOf<K_V>{V:>:Nil}
        Plist<K_V>))

  (et-defalias PlistGet [P K]
    (map-cases P
               [[V] (&PlistOf K V) V|Nil]
               [[P] P (plist-get-r P K)]))

  (et-defalias PlistPut [P K]
    (map-cases P
               [[V] (PlistOf K V) V|Nil]
               [[P] P (plist-get-w P K)]))

  (et-defalias AlistPut [PL PK PV]
    (infer PL [K V] Alist<K_V> Alist<K|PK_V|PV>
           Never))

  (et-defalias Sexp []
    (or Symbol String Number
        (Cons Sexp Sexp)
        (Vector Sexp)))
  (et-defalias Sexps [] List<Sexp>)
#+end_src
